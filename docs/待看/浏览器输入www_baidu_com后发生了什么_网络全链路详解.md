# 在浏览器输入 `www.baidu.com` 并回车后，究竟发生了什么

> 经典计算机网络面试题的完整拆解版。
>
> 本文以“Windows 10/11 笔记本、Chrome/Edge 类浏览器、Wi-Fi 接入家庭路由器、同时启用 IPv4/IPv6、没有显式代理或 VPN”为主线。现实环境可能使用 macOS/Linux、有线网、企业代理、校园网、VPN、手机热点或 HTTP/3；这些分支会在相应章节说明。
>
> 为避免把不同概念混在一起，本文始终区分：
>
> - **网页地址解析**：浏览器如何理解 `www.baidu.com`；
> - **名字解析**：HOSTS、缓存、DNS 如何把域名变成 IP；
> - **连接建立**：网卡、ARP/NDP、路由、TCP 或 QUIC；
> - **安全握手**：TLS 如何认证服务器并建立密钥；
> - **应用协议**：HTTP 请求和响应；
> - **页面呈现**：浏览器如何把响应变成屏幕上的网页。

---

## 0. 先给一个完整结论

用户在地址栏输入 `www.baidu.com`，回车后，典型过程可以概括为：

```text
键盘输入
  -> 浏览器解析地址
  -> 浏览器/操作系统查本地缓存和 HOSTS
  -> DNS 把域名解析成一个或多个 IP 地址
  -> 操作系统选择出口网卡和下一跳
  -> ARP 或 IPv6 NDP 找到网关的 MAC 地址
  -> Wi-Fi/以太网把 IP 数据包交给家庭路由器
  -> 路由器做 NAT、状态防火墙并转发到 ISP
  -> 互联网路由器依据路由表把包送到百度/CDN 边缘节点
  -> 建立 TCP+TLS，或直接建立 QUIC/HTTP3
  -> 浏览器发送 HTTP 请求
  -> 百度边缘节点、负载均衡器、WAF、反向代理和源站处理请求
  -> HTTP 响应沿相反方向返回
  -> 浏览器解压、解析 HTML/CSS/JS、下载子资源
  -> DOM + CSSOM -> 布局 -> 绘制 -> 合成 -> GPU/屏幕显示
```

这里至少涉及下列设备和软件：

| 类别 | 参与者 | 主要职责 |
|---|---|---|
| 人机输入 | 键盘、USB/Bluetooth 驱动、窗口系统 | 把按键变成浏览器可见字符 |
| 应用软件 | Chrome、Edge、Firefox | 地址解析、缓存、网络请求、HTML/CSS/JS 渲染 |
| 浏览器辅助进程 | Browser process、Renderer、Network Service、GPU process | 隔离页面、发起网络请求、执行脚本、绘制页面 |
| 操作系统 | Windows 网络栈、Winsock、DNS Client、路由表、防火墙 | 提供 socket、解析、路由、数据包收发和权限控制 |
| 驱动 | 网卡驱动、Wi-Fi 驱动、NDIS | 把操作系统的网络帧交给硬件 |
| 本地硬件 | 无线网卡/有线网卡、CPU、RAM、总线 | 编解码、缓存、发送和接收比特 |
| 局域网设备 | 无线 AP、交换机、家庭路由器 | 二层转发、DHCP、DNS 转发、NAT、防火墙 |
| 接入设备 | 光猫、Cable modem、校园网接入设备 | 把家庭/宿舍网络接入运营商网络 |
| 运营商网络 | BRAS、核心路由器、DNS 递归服务器、NAT 网关 | 接入认证、互联网转发、递归解析 |
| 互联网 | BGP 路由器、骨干链路、互联点 | 跨自治系统转发 IP 包 |
| 百度侧 | CDN/边缘节点、负载均衡、WAF、反向代理、源站、数据库/缓存 | 接收 HTTPS/HTTP 请求并生成响应 |

## 1. 先建立“从软件到电信号”的分层地图

### 1.1 五个常用观察层

面试时常用 OSI 七层模型，但实际排查更适合使用下面五层：

```text
应用层：HTTP、DNS、TLS（TLS 常被放在应用与传输之间）
传输层：TCP、UDP、QUIC
网络层：IPv4、IPv6、ICMP
链路层：Ethernet、Wi-Fi、ARP、IPv6 NDP
物理层：网线、光纤、无线电、网卡电信号
```

“浏览器打开网页”不是某一层单独完成的，而是多层逐层封装：

```text
HTTP 数据
  -> TLS 记录（如果是 HTTPS）
  -> TCP 字节流，或 QUIC UDP 数据报
  -> IP 数据包
  -> Ethernet/Wi-Fi 帧
  -> 电信号/无线电波
```

接收端执行反向解封装：

```text
无线电/电信号
  -> Wi-Fi/以太网帧
  -> IP 包
  -> TCP/QUIC
  -> TLS 解密
  -> HTTP
  -> 浏览器渲染
```

### 1.2 “包、段、帧、字节流”不要混淆

| 名称 | 通常所属层 | 典型含义 |
|---|---|---|
| 比特 | 物理层 | 0/1 的电、光或无线信号表示 |
| 帧 Frame | 链路层 | 一跳局域网传输的数据单元，带 MAC 地址 |
| 包 Packet | 网络层 | IP 层数据单元，带源/目的 IP |
| 段 Segment | TCP 语境 | TCP 头加 TCP 数据；UDP 常称 Datagram |
| QUIC packet | QUIC 语境 | 搭载 QUIC 帧的 UDP 数据报内逻辑单元 |
| HTTP message | 应用层 | HTTP 请求或响应 |
| TCP stream | 传输层 | 有序字节流，没有应用消息边界 |

例如，一个 HTTP 响应可能被 TLS 分成多个记录，再被 TCP 分成多个段，再被 IP 分成多个包，最后每一跳封装成不同的链路层帧。面试中说“HTTP 包”往往只是口语，严格表达应说明是哪一层。

### 1.3 数据平面、控制平面和管理平面

这条访问链里可以看到三种动作：

- **数据平面**：真正转发网页请求和响应的数据包；
- **控制平面**：BGP、路由协议、ARP/NDP 邻居发现等，决定数据怎么走；
- **管理平面**：浏览器代理设置、系统防火墙规则、路由器配置、证书信任库。

例如，BGP 不会替你传输某个 HTML 字节，它负责让路由器知道“去某个 IP 前缀应该走哪个邻居”。

## 2. 回车之前：你的笔记本已经做了哪些准备

很多面试答案从 DNS 开始，但 DNS 之前，笔记本必须已经接入网络。否则它没有 IP、没有默认网关，也无法发出 DNS 查询。

### 2.1 开机后的硬件和驱动

以 Windows 笔记本为例：

1. BIOS/UEFI 初始化 CPU、内存、PCIe/USB 设备和网卡；
2. Windows 内核加载无线网卡或有线网卡驱动；
3. 驱动向系统注册一个网络接口，例如 Wi-Fi 或 Ethernet；
4. 操作系统为该接口维护链路状态、MAC 地址、MTU、统计计数器和收发队列；
5. 浏览器、DNS Client 和其他应用通过系统 socket 接口使用这个接口。

网卡有一个链路层地址，通常称为 MAC 地址。例如：

```text
Wi-Fi 网卡 MAC = 3C-52-82-XX-XX-XX
```

实际地址可能启用随机化，尤其是 Wi-Fi 探测和连接时。MAC 地址只在局部链路中有意义，不能直接跨互联网路由。

### 2.2 Wi-Fi 连接过程

如果使用 Wi-Fi，笔记本和无线 AP 之间通常经历：

```text
扫描信道
  -> 发现 SSID/BSSID
  -> 认证与关联
  -> WPA2/WPA3 握手
  -> 建立加密的无线数据链路
```

这里的无线 AP 可能独立存在，也可能与家庭路由器集成在同一台设备里。

Wi-Fi 的无线帧与之后的 IP 包不是同一层对象。Wi-Fi 链路可能重传无线帧，但它不能替代 TCP 的端到端可靠性；无线链路重传成功，也不代表百度应用已经处理了 HTTP 请求。

### 2.3 DHCP：笔记本如何得到 IPv4 配置

家庭网络里，笔记本通常通过 DHCP 自动取得：

- IPv4 地址，例如 `192.168.1.23`；
- 子网掩码，例如 `255.255.255.0`；
- 默认网关，例如 `192.168.1.1`；
- DNS 服务器地址，例如路由器地址或运营商 DNS；
- 租约时间、域名搜索后缀等。

经典 DHCP DORA 流程：

```text
客户端                         DHCP 服务器/路由器
  |---- DHCPDISCOVER ----------->|  广播：有没有 DHCP 服务？
  |<--- DHCPOFFER ---------------|  提供一个地址和配置
  |---- DHCPREQUEST ------------>|  请求使用该配置
  |<--- DHCPACK -----------------|  确认租约
```

初始时客户端可能还没有可用 IPv4 地址，因此前两个消息常使用广播。DHCP 使用 UDP，服务器端口 67，客户端端口 68。

### 2.4 IPv6 的地址配置

如果网络启用 IPv6，笔记本可能同时得到：

- `fe80::/10` 链路本地地址；
- 路由器通告 RA 提供的全局前缀；
- SLAAC 自动生成的地址；
- 通过 DHCPv6 获得的其他参数。

IPv6 的默认网关通常不是由 DHCPv6 直接提供，而是通过 Router Advertisement 通告。IPv6 不使用 ARP，而使用 NDP（Neighbor Discovery Protocol，邻居发现协议）。

### 2.5 默认路由和 DNS 配置

得到配置后，系统路由表可能类似：

```text
192.168.1.0/24     直连 Wi-Fi 接口
0.0.0.0/0          192.168.1.1   默认路由
```

含义是：

- 去 `192.168.1.x` 的主机，直接在局域网找它；
- 其他 IPv4 目的地，先交给默认网关 `192.168.1.1`。

DNS 配置则告诉操作系统“通常向哪台递归解析器提问”。它可以是：

- 家庭路由器；
- 运营商 DNS；
- 公共 DNS；
- 公司/校园内网 DNS；
- 浏览器自己的 DoH 服务端。

### 2.6 家庭路由器自身做了什么

常见家用路由器同时承担：

- Wi-Fi AP；
- 交换机；
- DHCP 服务器；
- DNS 转发/缓存；
- 默认网关；
- NAT/PAT；
- 有状态防火墙；
- PPPoE、DHCP 或光猫上联。

因此“路由器”不是只有一个功能。它可能先回答 DNS，又在之后转发 HTTPS 数据。

## 3. 第一步：键盘输入如何到达浏览器

### 3.1 键盘、驱动和窗口系统

当你按下 `w`：

1. 键盘控制器检测按键；
2. 通过 USB、Bluetooth 或内置总线向操作系统发送输入事件；
3. Windows 键盘驱动和输入子系统将扫描码转换为虚拟键码；
4. 输入法/键盘布局决定最终字符；
5. 窗口系统把事件投递给当前获得焦点的浏览器窗口；
6. 浏览器地址栏组件更新文本。

按下回车时，浏览器收到一个“提交地址栏导航”的事件。

这一步一般不经过网络。网络活动从浏览器决定要导航到哪个 URL 之后才开始。

### 3.2 浏览器如何判断这是网址还是搜索词

地址栏通常同时具有：

- URL 输入框；
- 搜索框。

浏览器会依据字符串形态判断：

```text
www.baidu.com       看起来像主机名 -> 按 URL 处理
北京天气            没有明显主机结构 -> 交给默认搜索引擎
https://example.com  明确是 URL
```

具体规则由浏览器实现和设置决定。如果输入包含空格，或者被浏览器判断为搜索词，后续访问的可能是搜索引擎，而不是百度网站本身。

### 3.3 URL 规范化

浏览器会把输入规范化为类似：

```text
scheme   = https（现代浏览器通常优先 HTTPS；具体策略因浏览器而异）
host     = www.baidu.com
port     = 443（HTTPS 默认端口）
path     = /
query    = 空
fragment = 空
```

这里不要把“用户只输入了域名”和“服务器最终收到的请求”混为一谈。浏览器可能：

- 自动补 `https://`；
- 先尝试 HTTPS；
- 因 HSTS 或 HTTPS-First 策略拒绝明文 HTTP；
- 遇到重定向后变成另一个 URL；
- 根据历史、缓存或站点策略改变路径。

最终请求的准确 URL 应在浏览器开发者工具的 Network 面板中查看。

### 3.4 Origin 和 Host

对 `https://www.baidu.com/`，浏览器可以把 origin 表示为：

```text
scheme = https
host   = www.baidu.com
port   = 443
```

HTTP/1.1 请求通常有 `Host: www.baidu.com`；HTTPS 握手中还会在 TLS ClientHello 里发送 SNI（Server Name Indication），告诉服务器希望访问哪个主机名。两者作用不同：

- **SNI**：TLS 握手早期选择证书和虚拟主机；
- **Host**：HTTP 层选择具体站点。

### 3.5 浏览器进程架构

现代浏览器通常不是一个单进程：

```text
Browser/UI Process
  - 地址栏、标签页、权限、Cookie、导航

Network Service
  - DNS、连接池、代理、HTTP、缓存、TLS 接口

Renderer Process
  - HTML/CSS/JavaScript、DOM、布局、页面脚本

GPU Process
  - 图层合成、纹理和硬件加速

其他进程
  - 扩展、音频、崩溃报告、沙箱辅助等
```

不同浏览器具体拆分不同，但“浏览器 UI”和“网页 JavaScript”通常被隔离，网页不能任意调用操作系统网络 API。

## 4. 第二步：浏览器先查哪里？HOSTS 文件到底是什么

### 4.1 HOSTS 文件的作用

HOSTS 是一个本地静态主机名映射文件，可以把名字直接映射到 IP：

```text
203.0.113.10    www.example.test
```

在 Windows 上，通常路径是：

```text
C:\Windows\System32\drivers\etc\hosts
```

文件没有 `.txt` 扩展名。典型格式：

```text
# 注释
127.0.0.1       localhost
::1             localhost
192.168.1.50    internal.example
```

HOSTS 是本机管理员可修改的静态数据，不是 DNS 服务器，也不会自动从互联网更新。

### 4.2 HOSTS 的优先级

对于 Windows 系统解析器，一个常见的简化顺序是：

```text
应用/浏览器自己的缓存
  -> 操作系统 DNS/名称解析缓存
  -> HOSTS 文件
  -> 配置的 DNS 服务器
```

但要注意两个例外：

1. 浏览器可能自己实现 DNS、使用 DoH，绕过部分系统解析路径；
2. 企业策略、VPN、代理和安全软件可能改变解析顺序。

因此“HOSTS 一定先于浏览器缓存”不应当作为所有浏览器的绝对定律。面试中可说：**系统解析器通常会检查 HOSTS，但浏览器自己的缓存和安全策略可能在更前面。**

### 4.3 如果 HOSTS 中写了百度域名

假设管理员在 HOSTS 中写入：

```text
192.0.2.99    www.baidu.com
```

那么系统解析器可能直接返回 `192.0.2.99`，而不向 DNS 查询。后续浏览器会尝试连接这个地址。

结果可能是：

- 连接到内部测试服务器；
- 连接超时；
- TLS 证书与 `www.baidu.com` 不匹配；
- 被防火墙拦截；
- 看到完全错误的站点。

这就是为什么“改 HOSTS”可以做开发测试，也可能造成域名劫持和排障误判。

### 4.4 HOSTS 的安全风险

恶意软件可能修改 HOSTS，把：

```text
bank.example -> 攻击者 IP
```

用户看到的地址栏仍然是原域名，但 TCP 连接已经去了错误地址。HTTPS 证书校验通常会阻止不匹配的服务器，但如果用户忽略证书警告、系统信任库被植入恶意根证书，风险会增加。

### 4.5 127.0.0.1、0.0.0.0 和本地回环

常见屏蔽写法：

```text
127.0.0.1    ads.example
0.0.0.0      ads.example
```

这不是“DNS 返回了本机地址”，而是本机配置的静态映射。浏览器随后可能连接本机回环接口或不可路由地址。

### 4.6 DNS Client 缓存

Windows 还可能运行 DNS Client 服务并缓存最近的解析结果。缓存记录通常带 TTL（Time To Live，生存时间），到期后需要重新查询。

查看缓存：

```powershell
ipconfig /displaydns
```

清除缓存：

```powershell
ipconfig /flushdns
```

清缓存不会清浏览器 HTTP 缓存、Cookie、连接池，也不会修复错误的 HOSTS 文件或代理设置。

## 5. 第三步：DNS 如何把 `www.baidu.com` 变成 IP

### 5.1 DNS 解决的只是“名字到地址”

浏览器需要连接一个 IP 地址，但人类输入的是域名。DNS 负责回答类似：

```text
www.baidu.com -> IPv4 A 记录和/或 IPv6 AAAA 记录
```

DNS 不负责：

- 建立 TCP；
- 验证 HTTPS 证书；
- 传输 HTML；
- 判断网页是否可用。

DNS 成功只能说明“得到了一些候选地址”，不能说明百度网站已经响应。

### 5.2 浏览器和系统可能先查多个缓存

典型候选来源：

1. 浏览器内存 DNS 缓存；
2. 浏览器连接池中已有可复用连接；
3. 浏览器/系统缓存的正向 DNS 记录；
4. HOSTS 文件；
5. 操作系统 DNS Client 缓存；
6. 本地安全软件或 VPN 的 DNS 代理；
7. 配置的递归 DNS 服务器；
8. 浏览器启用的 DoH 服务。

如果已有有效连接，甚至可能不需要重新做 DNS 查询。

### 5.3 `getaddrinfo` 和 Winsock

传统 Windows 应用可以通过 Winsock API 请求解析：

```c
getaddrinfo("www.baidu.com", "https", ...)
```

这不是说浏览器一定直接调用这个函数，而是说明应用通常通过操作系统提供的名称解析和 socket 抽象获得地址。浏览器也可以拥有自己的 DNS 模块。

解析结果可能包含：

```text
IPv6 地址 AAAA 记录
IPv4 地址 A 记录
别名 CNAME 链
```

### 5.4 A、AAAA、CNAME、NS、TTL

| DNS 类型 | 含义 |
|---|---|
| A | 主机名到 IPv4 地址 |
| AAAA | 主机名到 IPv6 地址 |
| CNAME | 一个名字是另一个名字的别名 |
| NS | 某个域的权威名称服务器 |
| SOA | 区域的管理起点和序列信息 |
| TXT | 文本型元数据，常用于验证和策略 |
| MX | 邮件服务器，不用于普通网页连接 |

TTL 告诉缓存“这个答案可以缓存多久”。TTL 到期不代表网页立刻不可用，只代表下一次解析可能要重新查询。

### 5.5 递归 DNS 的工作

笔记本通常不会自己从根服务器一路查到百度权威服务器，而是向一个递归解析器提问：

```text
笔记本 -> 家庭路由器/运营商/公共 DNS 递归解析器
```

递归解析器可能已经缓存答案。如果没有缓存，它大致会：

```text
递归解析器 -> 根 DNS：谁负责 .com？
递归解析器 -> .com TLD DNS：谁负责 baidu.com？
递归解析器 -> baidu.com 权威 DNS：www.baidu.com 的 A/AAAA 是什么？
```

实际 DNS 服务器地址、缓存、预取、DNSSEC、EDNS 和运营商实现会影响细节。

### 5.6 根、TLD 和权威服务器分别是什么

- **根服务器**：不直接回答所有网站 IP，而是告诉你顶级域 `.com` 的服务器在哪里；
- **TLD 服务器**：例如 `.com` 服务器，告诉你 `baidu.com` 的权威 DNS；
- **权威 DNS**：负责 `baidu.com` 区域内的正式记录；
- **递归解析器**：替客户端执行查询并缓存结果。

常见误解是“根 DNS 知道百度 IP”。更准确的是，根和 TLD 负责委派，权威 DNS 才负责具体区域记录。

### 5.7 DNS 查询用什么协议

传统方式：

```text
客户端 -> UDP 53 -> 递归 DNS
```

如果响应太大、需要可靠传输或发生特定情况，DNS 可以使用 TCP 53。

加密方式：

- **DoT**：DNS over TLS，通常 TCP 853；
- **DoH**：DNS over HTTPS，复用 HTTPS 通道，通常 TCP 443 或 HTTP/3。

DoH 可能由浏览器直接访问配置的服务端，因此本地路由器未必能看到普通 UDP 53 查询。

### 5.8 DNS 查询本身也需要网络路径

如果没有缓存，DNS 查询不是“凭空发生”：

1. 系统找到 DNS 服务器 IP；
2. 判断 DNS 服务器是否在本地子网；
3. 如果不在，先找到默认网关 MAC；
4. 把 UDP/TCP/HTTPS DNS 请求发送给网关；
5. 路由器再把它转发到 DNS 服务器；
6. 递归解析器完成后返回结果。

所以 DNS 通常发生在网页连接之前，但 DNS 自己也要经过网卡、链路、路由和防火墙。

### 5.9 DNS 返回多个地址怎么办

一个域名可能返回多个 A/AAAA 地址，用于：

- 高可用；
- 负载分散；
- CDN 就近接入；
- IPv4/IPv6 双栈；
- 故障切换。

浏览器和操作系统可能对地址排序，并使用 Happy Eyeballs 类策略并行或交错尝试 IPv6/IPv4。不能简单说“先返回的 IP 一定使用”。

### 5.10 DNS 结果不等于百度“源站 IP”

大型网站通常把域名解析到边缘节点、负载均衡器或 CDN 地址。你得到的 IP 可能属于：

```text
百度/合作 CDN 的边缘接入点
  -> 反向代理/负载均衡
  -> 内部服务
```

它不一定是实际存放 HTML 或数据库的机器，也不应把公开解析结果当作源站拓扑图。

## 6. 第四步：操作系统如何决定从哪个网卡发出去

DNS 返回 IP 后，浏览器还没有真正把网页请求发出去。它要把目标地址交给操作系统，操作系统进行路由查找。

### 6.1 浏览器创建连接请求

浏览器的网络服务会向系统请求一个连接，概念上类似：

```text
connect(destination_ip, destination_port=443)
```

实际参数可能包括：

- 目标 IPv4 或 IPv6 地址；
- 目标端口 443；
- 代理设置；
- socket 类型；
- 超时和取消信号；
- 是否尝试 QUIC/HTTP3。

如果浏览器配置了 HTTP/SOCKS 代理，目标地址可能先变成代理服务器地址，而不是直接连接百度 IP。这是后文的一个重要分支。

### 6.2 路由表查找

操作系统根据目标 IP 查路由表，核心规则是**最长前缀匹配**：匹配得更具体的网络优先。

示例：

```text
目标：180.101.x.x

192.168.1.0/24 -> Wi-Fi 直连       不匹配
10.0.0.0/8      -> VPN 接口        不匹配
0.0.0.0/0      -> 192.168.1.1     匹配默认路由
```

于是系统决定：

```text
出口接口 = Wi-Fi
下一跳   = 192.168.1.1
```

如果目标 IP 在本地子网，例如 `192.168.1.80`，下一跳可能就是目标主机本身，不需要经过默认网关。

### 6.3 多网卡场景

笔记本可能同时有：

- Wi-Fi；
- Ethernet 有线网卡；
- VPN 虚拟网卡；
- Docker/WSL 虚拟网卡；
- 手机 USB 共享网络；
- 蓝牙网络适配器。

路由表和接口 metric 决定优先级。VPN 通常会插入更具体的路由，或者设置全局默认路由，把所有流量先送进 VPN 隧道。

### 6.4 源 IP 和临时端口

建立 TCP 连接时，客户端还需要选择：

- 本机源 IP，例如 `192.168.1.23`；
- 临时源端口，例如 `53142`；
- 目标 IP，例如解析得到的某个百度边缘地址；
- 目标端口 `443`。

连接四元组可以表示为：

```text
192.168.1.23:53142  ->  203.0.113.20:443
```

真实百度地址会变化，本文故意使用文档示例地址，不把示例数字当作当前真实解析结果。

### 6.5 socket 是什么

socket 不是一根网线，也不是一个 IP 地址，而是操作系统提供的通信抽象。应用通过 socket：

- 创建连接；
- 读写字节；
- 设置超时；
- 查询错误；
- 关闭连接。

内核为 socket 保存发送缓冲区、接收缓冲区、协议状态、四元组、拥塞控制和安全相关状态。应用调用 `send()` 时，数据通常先进入内核缓冲区，不代表已经到达百度。

## 7. 第五步：ARP、NDP、网关 MAC 和网卡到底做了什么

### 7.1 IP 地址不等于 MAC 地址

IP 用于网络层寻址和跨网络路由；MAC 用于当前链路上的帧投递。笔记本不能把一个互联网 IP 直接写进 Wi-Fi 帧的目的 MAC 字段。

如果目标不在本地子网，笔记本要找的是**默认网关的 MAC**，不是百度服务器的 MAC。

```text
目标 IP = 百度边缘 IP
下一跳 IP = 家庭路由器内网地址 192.168.1.1
需要解析的 MAC = 路由器 Wi-Fi 接口 MAC
```

### 7.2 IPv4 ARP

如果网关 MAC 不在 ARP 缓存中，笔记本广播 ARP Request：

```text
广播：谁拥有 192.168.1.1？请告诉 192.168.1.23
```

家庭路由器回复 ARP Reply：

```text
192.168.1.1 的 MAC 是 AA:BB:CC:DD:EE:FF
```

笔记本把映射放入邻居/ARP 缓存，随后把 IP 包封装进目的 MAC 为路由器的以太网或 Wi-Fi 帧。

查看 Windows ARP/邻居缓存：

```powershell
arp -a
Get-NetNeighbor
```

### 7.3 IPv6 NDP

IPv6 使用 ICMPv6 Neighbor Solicitation/Advertisement：

```text
Neighbor Solicitation：谁拥有这个 IPv6 下一跳？
Neighbor Advertisement：这个地址对应我的链路层地址
```

NDP 还负责：

- 路由器发现；
- 地址重复检测；
- 邻居可达性检测；
- 前缀和默认路由通告。

### 7.4 链路层帧的概念结构

以太网帧可以抽象成：

```text
目的 MAC
源 MAC
EtherType（例如 IPv4/IPv6）
IP 数据包
帧校验序列 FCS
```

Wi-Fi 帧字段更多，可能有 BSSID、序列号、QoS、加密保护等。无线 AP 收到帧后，会把它转换/桥接到有线侧或路由侧。

### 7.5 Wi-Fi 不是“空气中的 TCP”

Wi-Fi 负责局部无线链路，典型动作包括：

- 监听信道；
- 竞争发送机会；
- 使用 ACK 确认无线帧；
- 碰撞避免；
- 重传丢失的无线帧；
- WPA 加密和解密。

这些机制发生在链路层，不会让应用直接看到“无线帧重传”。应用最终只看到 socket 字节是否按时到达。

### 7.6 MTU 和帧大小

以太网常见 MTU 是 1500 字节，但隧道、PPPoE、VPN 和某些网络可能更小。IP 包太大时可能：

- IPv4 分片；
- IPv6 由发送端通过 Path MTU Discovery 调整；
- 中间设备丢弃并返回 ICMP Packet Too Big；
- TCP 分段成适合路径的大小。

浏览器不会直接按“一个网页一个以太网帧”发送。大响应会跨越很多帧、包和 TCP 段。

## 8. 第六步：家庭路由器、NAT 和防火墙

### 8.1 路由器收到什么

家庭路由器从 Wi-Fi 收到一帧后，大致执行：

1. 校验链路层帧；
2. 解封装得到 IP 包；
3. 检查目的 IP 是否是路由器自身；
4. 如果是 DNS 请求、DHCP 或管理流量，交给本地服务；
5. 如果是去互联网的数据，查 WAN 路由；
6. 应用 NAT/PAT 和防火墙规则；
7. 重新封装成 WAN 链路需要的帧并发送。

### 8.2 NAT/PAT 改写什么

家庭内网地址通常是私有地址，不能直接在公共互联网路由：

```text
192.168.1.23:53142 -> 203.0.113.20:443
```

路由器可能改成：

```text
公网地址:62001 -> 203.0.113.20:443
```

路由器保存映射表：

```text
内网 192.168.1.23:53142
外网 公网IP:62001
目标 203.0.113.20:443
```

响应返回时，路由器依据这张状态表把目标端口和地址改回内网主机。

NAT 不只是“改 IP”，通常还改 TCP/UDP 端口，并重新计算校验和。对 IPv6 端到端场景，可能不需要传统 NAT，但仍有防火墙和前缀策略。

### 8.3 为什么返回包知道该给哪台笔记本

因为路由器的有状态 NAT 表记录了出站连接。收到：

```text
203.0.113.20:443 -> 公网IP:62001
```

路由器查表后变成：

```text
203.0.113.20:443 -> 192.168.1.23:53142
```

再在局域网中通过 ARP/NDP 找到笔记本的 MAC。

### 8.4 有状态防火墙

家庭路由器通常允许“内网主动建立的连接”的返回流量，但拒绝互联网主动发起的陌生入站连接。它会检查：

- 五元组；
- TCP 标志位；
- 连接状态；
- 超时；
- 黑名单/白名单；
- 异常包和扫描行为。

这解释了为什么你通常能访问外部 HTTPS，却不能让外部任意访问家里笔记本的 443 端口。

### 8.5 CGNAT 和多层 NAT

运营商可能再做一层 Carrier-Grade NAT：

```text
笔记本私网 -> 家庭路由器 NAT -> 运营商 CGNAT -> 互联网
```

这会影响入站连接、端口可见性、部分 P2P 和故障排查，但一般不改变你访问百度的基本流程。

### 8.6 代理不是 NAT

如果浏览器使用 HTTP/SOCKS 代理：

```text
浏览器 -> 代理服务器 -> 百度
```

浏览器可能把 DNS 和 TCP 连接交给代理，或者只把 HTTPS 隧道交给代理。代理是应用层/会话层参与者，NAT 是网络边界上的地址映射，二者不能混称。

### 8.7 VPN 的变化

VPN 会创建虚拟网卡和加密隧道：

```text
浏览器 -> VPN 虚拟网卡 -> 加密隧道 -> VPN 网关 -> 百度
```

本机路由可能把百度 IP 送入 VPN；DNS 也可能被 VPN 接管。外部看到的源 IP 通常是 VPN 出口地址，而不是家庭公网地址。

## 9. 第七步：运营商和互联网路由器如何把包送到百度

### 9.1 每个路由器只需要决定下一跳

互联网路由器不需要知道完整应用请求，也不需要知道网页 HTML。它主要看 IP 头：

```text
目的 IP
源 IP
TTL/Hop Limit
协议号（TCP、UDP、ICMP 等）
```

查路由表后，选择下一跳接口，减少 TTL，然后重新封装链路层帧。

### 9.2 路由器逐跳处理

一个简化路径：

```text
笔记本
  -> 家庭路由器
  -> 光猫/接入设备
  -> 运营商接入路由器
  -> 运营商城域/省级核心
  -> 运营商出口
  -> 互联网互联点
  -> 百度/ CDN 上游
  -> 百度边缘节点
```

实际可能更短、更长或发生绕路。`tracert` 显示的是探测包对沿途设备的部分反馈，不一定等同于 HTTPS 数据的完整路径。

### 9.3 BGP 和自治系统

互联网由许多自治系统（AS）组成：

- 运营商 AS；
- 云厂商 AS；
- 内容提供商 AS；
- 企业和教育网 AS。

BGP 在自治系统之间传播可达前缀和路径属性。路由选择考虑本地策略、路径长度、优先级和其他属性，不是简单的“物理距离最短”。

因此 DNS 的“就近”与 BGP 的实际路径共同影响你最终访问哪个边缘节点。

### 9.4 TTL/Hop Limit

IPv4 的 TTL 和 IPv6 的 Hop Limit 每经过一个三层路由器通常减 1。减到 0 时，路由器丢弃包并可能返回 ICMP Time Exceeded。`tracert/traceroute` 利用这个机制逐步探测路径。

TTL 不是 TCP 生存时间，也不是 HTTP 缓存 TTL。三个“TTL”概念经常被初学者混淆：

| 名称 | 所属位置 | 作用 |
|---|---|---|
| IP TTL/Hop Limit | IP 头 | 限制三层跳数 |
| DNS TTL | DNS 记录 | 限制缓存时间 |
| HTTP Cache-Control max-age | HTTP 头 | 控制资源缓存时间 |

### 9.5 丢包、重传和拥塞

互联网链路可能出现：

- 无线干扰；
- 队列溢出；
- 路由切换；
- 链路故障；
- 设备限速。

TCP 会根据 ACK、重复 ACK、超时和拥塞窗口调整发送速度。应用通常不直接看到某个 TCP 段被重传，只会观察到延迟增加或连接失败。

### 9.6 ICMP 的作用

ICMP 可以用于：

- ping 回显；
- TTL 超时；
- 目的不可达；
- IPv6 Packet Too Big；
- 路径 MTU 反馈。

禁止 ping 不等于 HTTPS 不通；很多服务器或防火墙会丢弃 ICMP Echo，但仍允许 TCP 443。

### 9.7 从 CPU 到电波：一次发送动作经过哪些硬件

前面的描述容易让人以为“浏览器直接把数据交给网线”。实际链条大致是：

```text
浏览器进程
  -> 内核 socket/协议栈
  -> 内核内存中的发送缓冲区
  -> 网卡驱动
  -> 网卡 DMA 读取内存
  -> 网卡的发送队列和硬件校验/封装
  -> Wi-Fi 射频芯片或以太网 PHY
  -> 天线发射电磁波，或双绞线传输电信号
  -> 无线路由器/AP 的接收芯片
```

这里的“网卡”可能是：

- 笔记本内置的 Wi-Fi 网卡，包含基带、射频前端、天线接口和固件；
- USB Wi-Fi 网卡；
- 有线以太网控制器，之后还会经过 PHY 芯片、网口磁性器件和网线；
- VPN 创建的虚拟网卡，它本身不发射信号，而是把包交给真实网卡上的隧道程序。

CPU 通常负责协议栈和控制逻辑，但不会逐位地用指令“拨动”网线。网卡利用 DMA（Direct Memory Access）从内存读取数据，减少 CPU 拷贝；发送完成后通过中断或轮询通知驱动。现代系统还可能使用校验和卸载、分段卸载、接收合并等功能，因此抓包工具看到的包大小和网卡线上真正发送的分段，在某些位置可能不同。

Wi-Fi 还要处理信道竞争、调制编码、重传确认、加密和省电唤醒。一次 TCP 重传可能是 TCP 层发现端到端丢包，也可能是 Wi-Fi 链路层已经在本地重发了多次仍失败。两种重传的计时器和观察位置不同。

## 10. 第八步：TCP 连接如何建立

以下以浏览器选择 IPv4、使用 HTTPS、服务器端口 `443` 为例。若浏览器选择 IPv6，IP 头和邻居发现不同，但 TCP 的核心握手相同。

### 10.1 为什么通常是端口 443

`www.baidu.com` 是主机名，不包含端口。浏览器根据 URL 的 scheme 推导默认端口：

| URL scheme | 默认端口 | 典型传输 |
|---|---:|---|
| `http` | 80 | TCP + HTTP/1.1 或 HTTP/2（较少见） |
| `https` | 443 | TCP + TLS + HTTP/1.1/2 |
| `https` + HTTP/3 | 443 | UDP + QUIC + HTTP/3 |

现代浏览器可能把用户输入的裸域名升级为 HTTPS。升级来源可能是历史缓存、HSTS、浏览器安全策略、搜索/地址栏策略或服务器重定向；具体行为不应被简化为“浏览器永远先访问 HTTP 80”。

### 10.2 四元组和临时端口

一条 TCP 连接通常由四元组标识：

```text
源 IP、源端口、目的 IP、目的端口
```

例如（均为示例）：

```text
192.168.1.23:53142  ->  203.0.113.20:443
```

`53142` 是操作系统为本次出站连接选择的临时源端口。多个标签页可以同时访问同一个服务器，因为它们使用不同源端口、不同源地址，或复用不同的连接。家庭路由器做 NAT 后，公网侧还可能看到另一组源 IP 和源端口。

端口不是物理插座，而是操作系统把收到的字节交给哪个 socket 的逻辑编号。服务器监听 `443`，客户端通常不监听固定端口。

### 10.3 三次握手逐包发生什么

简化时序如下：

```text
客户端                                      服务器
  | --- SYN, Seq=x ------------------------> |
  | <--- SYN+ACK, Seq=y, Ack=x+1 ---------- |
  | --- ACK, Ack=y+1 ----------------------> |
  |        TCP 连接进入 ESTABLISHED          |
```

1. 客户端发送 `SYN`，表示请求建立连接，并携带初始序列号 `x`、最大报文段长度 MSS、窗口扩大因子、SACK 能力等选项。
2. 服务器若允许连接，返回 `SYN+ACK`，自己的初始序列号为 `y`，确认客户端的 SYN：`Ack=x+1`。SYN 本身会消耗一个序列号。
3. 客户端返回 ACK，确认服务器的 SYN：`Ack=y+1`。此时双方都知道对方能接收并发送，连接可传输应用数据。

三次并不是为了“礼貌握手”，而是让双方交换并确认双向初始序列空间，避免旧连接残留报文被误认成新连接。服务器也可能因监听队列满、策略拒绝、端口关闭而返回 `RST` 或静默丢弃。

### 10.4 序列号、确认号和可靠字节流

TCP 不把网页理解为一条条完整消息，而是提供有序、可靠的字节流。假设客户端发送序列号从 `1000` 开始、这次携带 1200 字节，则服务器确认号可能变为 `2200`。确认号通常表示“下一个我期待的字节编号”，而不是“最后一个已收到的编号”。

TCP 可以乱序到达；接收端会暂存乱序数据，向发送端报告累计 ACK 或 SACK 块。发送端若发现重复 ACK、SACK 缺口或超时，会重传缺失数据。应用只在内核确认按序数据后通过 `recv` 读到它。

### 10.5 接收窗口、拥塞窗口和发送速度

发送量同时受到两个窗口约束：

- 接收窗口 `rwnd`：接收端缓冲区还能容纳多少，防止接收端被压垮；
- 拥塞窗口 `cwnd`：发送端根据网络拥塞估计允许在途多少，防止网络被压垮。

可粗略理解为：可发送的在途数据不超过 `min(rwnd, cwnd)`。TCP 会经历慢启动、拥塞避免、快速重传/恢复等阶段；不同操作系统和版本的算法可能不同。丢包不一定意味着服务器宕机，也可能只是无线或中间链路拥塞。

### 10.6 MSS、MTU、分段和校验

以太网常见 MTU 为 1500 字节。IPv4 TCP 的典型 MSS 约为 `1500 - 20(IP) - 20(TCP) = 1460`，但 TCP 选项、隧道、PPPoE、VPN、IPv6 等都可能改变它。MSS 是 TCP 负载建议值，MTU 是某条链路能承载的 IP 包大小，二者不是同一个概念。

IP 层可能分片（IPv4），IPv6 路由器不负责分片，过大的包通常通过 ICMP 反馈；TCP 也会依据路径信息调整分段。TCP、IP、链路层各自有校验或完整性机制，但这些不等同于 HTTPS 的端到端加密认证。

### 10.7 重传、超时和连接失败的表现

如果 SYN 没有得到响应，客户端会按实现进行指数退避重传，最终报告连接超时；如果对端明确拒绝，常见表现是 `Connection refused` 或收到 RST。连接建立后收到 RST，可能是服务进程关闭、状态丢失、防火墙主动拒绝或协议异常。应用层看到的错误文字由浏览器和操作系统重新解释，不能仅凭一句错误提示定位具体链路位置。

### 10.8 连接复用和连接池

加载百度首页后，浏览器通常不会为每张图片都重新做完整握手。它会：

- 复用 HTTP/1.1 的 keep-alive 连接；
- 在 HTTP/2 中用多个 stream 复用一条 TCP/TLS 连接；
- 在 HTTP/3 中用多个 QUIC stream 复用一条 UDP/QUIC 连接；
- 按域名、代理、网络隔离键、证书和协议能力维护连接池。

因此“输入一次网址”可能只发生一次 DNS 和一次握手，也可能因缓存、连接已存在、重定向、不同静态资源域名而产生多次连接。

## 11. 第九步：QUIC 和 HTTP/3 的另一条路径

### 11.1 QUIC 为什么使用 UDP

QUIC 把可靠传输、拥塞控制、流、多路复用和 TLS 1.3 集成在用户态协议中，使用 UDP `443` 作为外层承载。UDP 只提供无连接数据报，可靠性和安全性由 QUIC 自己实现；因此“HTTP/3 使用 UDP”不等于“HTTP/3 不可靠”或“不加密”。

### 11.2 QUIC 的握手

概念上可以表示为：

```text
客户端 -> UDP Initial + QUIC/TLS ClientHello
服务器 -> UDP Initial/Handshake + TLS ServerHello/证书/参数
客户端 -> ACK + 加密的应用数据
```

QUIC 的 TLS 1.3 握手和密钥派生紧密结合，通常可以减少传统 TCP + TLS 的串行等待。连接使用 Connection ID 标识，不完全依赖四元组，因此网络切换（例如 Wi-Fi 切到移动热点）时可以尝试迁移连接。

### 11.3 QUIC stream 和 TCP 队头阻塞

HTTP/2 虽然有多个 stream，但所有 stream 共享一条 TCP 有序字节流；某个 TCP 段丢失时，后续字节在 TCP 层等待，形成连接级队头阻塞。QUIC 在传输层区分独立 stream，一个 stream 的丢包通常不必阻塞其他 stream。

### 11.4 0-RTT 的代价

如果客户端保存了此前连接的会话票据，QUIC/TLS 可能使用 0-RTT 发送早期数据，降低重复访问延迟。0-RTT 数据可能被重放，因此服务器不应把不可重复的副作用操作（例如扣款）直接放在没有额外防重放措施的 0-RTT 请求中。初次访问通常仍需完整握手。

### 11.5 浏览器怎样选择 HTTP/2 或 HTTP/3

浏览器会综合考虑：

- DNS 返回的地址和网络可达性；
- `Alt-Svc` 等服务器提示；
- 过去成功的协议记录；
- UDP 是否被防火墙阻断；
- 连接竞速和失败回退策略。

如果 QUIC 不可用，浏览器通常回退到 TCP + TLS + HTTP/2 或 HTTP/1.1。故障排查时不能把“浏览器开发者工具显示 h2”理解为 DNS 或 TCP 没有发生，只能说明最终应用协议选择。

## 12. 第十步：TLS/HTTPS 如何建立安全通道

### 12.1 HTTPS 保护的是什么

HTTPS 通常是 HTTP 运行在 TLS 之上。TLS 主要提供：

- 机密性：旁路观察者难以读出 HTTP 内容；
- 完整性：篡改会被检测；
- 身份认证：通过证书验证服务器对域名的控制关系。

TLS 不保证服务器业务逻辑一定诚实，也不隐藏所有元数据。对端 IP、连接时间、流量大小等信息可能仍可被观察；DNS 若未加密也可能暴露查询名。

### 12.2 TLS 1.3 握手的概念时序

在 TCP 已建立后，可简化为：

```text
客户端                                      服务器
  | -- ClientHello ------------------------> |
  |    版本、密码套件、随机数、SNI、ALPN、密钥份额
  | <--- ServerHello ---------------------- |
  | <--- EncryptedExtensions -------------- |
  | <--- Certificate ---------------------- |
  | <--- CertificateVerify ---------------- |
  | <--- Finished ------------------------- |
  | -- Finished + HTTP request ------------> |
```

TLS 1.3 常用 ECDHE 密钥交换：双方交换临时公钥材料，各自计算共享秘密，再通过 HKDF 派生握手密钥和应用数据密钥。服务器私钥通常用于签名证明，而不是直接把所有 HTTP 数据用 RSA 加密。

### 12.3 SNI、证书和域名校验

`www.baidu.com` 可能与许多域名共享一个 IP。客户端在 ClientHello 中发送 SNI，告诉服务器希望访问的主机名，使服务器选择正确证书和虚拟主机配置。服务器证书链通常包含叶子证书和一个或多个中间 CA；客户端用操作系统或浏览器信任库中的根 CA 验证链。

客户端还会检查：

- 证书的 SAN 是否包含请求主机名；
- 当前时间是否在有效期内；
- 用途和签名算法是否允许服务器认证；
- 链是否能建立到受信任根；
- 必要时检查吊销状态或浏览器的额外策略。

SNI 是 TLS 握手中的名字，HTTP `Host` 是应用层请求头。两者通常相同，但层次和出现时机不同：SNI 在 HTTP 请求加密之前就可能可见（传统 TLS 1.2/1.3 场景），`Host` 在 TLS 加密通道内部发送。ECH 等机制可进一步保护部分 SNI 信息，但部署并非处处一致。

### 12.4 ALPN：协商 HTTP/1.1、HTTP/2 或其他协议

客户端在 ALPN 中声明支持的应用协议，例如：

```text
h2, http/1.1
```

服务器选择一个共同协议。HTTP/3 的协商通常与 QUIC/TLS 和 `h3` 标识有关。ALPN 不是 DNS，也不是端口；它是在安全握手中协商“连接上究竟说哪种应用协议”。

### 12.5 TLS Record 和对称加密

握手完成后，HTTP 数据被切分为 TLS Record，用对称 AEAD 算法加密并认证。对称加密速度快，适合大量网页数据；握手阶段的非对称签名和密钥交换主要用于协商密钥与证明身份。浏览器收到记录后验证认证标签，失败则丢弃并报告连接错误，不会把疑似篡改的数据交给 HTML 解析器。

### 12.6 证书错误、代理和中间人

以下情况可能导致浏览器警告或拒绝：证书过期、域名不匹配、未知 CA、链不完整、系统时间错误、企业代理重新签发证书但根证书未被信任等。HTTPS 并不意味着“任何拿到 IP 的服务器都能通过验证”；证书校验把“我连到了某个 IP”提升为“这个端点被可信 CA 认证为该域名”。

在企业 HTTPS 代理中，可能存在两段 TLS：客户端到代理、代理到目标站点。代理若安装了企业根 CA，可以解密并重新加密流量；这改变了端到端信任边界。VPN 通常在更低层封装流量，不必然终止目标网站的 TLS。

## 13. 第十一步：浏览器发送 HTTP 请求

### 13.1 HTTP/1.1 的直观示例

若协商到 HTTP/1.1，解密后的请求在逻辑上类似：

```http
GET / HTTP/1.1
Host: www.baidu.com
Connection: keep-alive
User-Agent: ExampleBrowser/1.0 (Windows 10; x64)
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8
Accept-Encoding: gzip, deflate, br, zstd
Accept-Language: zh-CN,zh;q=0.9,en;q=0.8
Cache-Control: max-age=0
Cookie: session_id=example-session
Sec-Fetch-Dest: document
Sec-Fetch-Mode: navigate
Sec-Fetch-Site: none
Upgrade-Insecure-Requests: 1

```

这是应用层语义示例，不代表某一浏览器此刻会逐字发送这些字段。请求通常没有 body，因为初次导航是 GET；服务器可根据 Cookie、地区、设备、实验分组和其他请求头生成不同响应。

### 13.2 HTTP/2 的二进制帧

HTTP/2 不把请求作为一整段文本在线上发送，而是使用二进制帧，例如 `HEADERS` 和 `DATA`。头部通过 HPACK 压缩，多个 stream 共享连接；一个请求对应一个 stream ID。抓包时看见的是 TLS 加密记录和 HTTP/2 帧，不能直接按 HTTP/1.1 文本查找完整请求行。

### 13.3 HTTP/3 的帧和 stream

HTTP/3 把 HTTP 语义映射到 QUIC stream，使用 QPACK 压缩头部。HTTP/3 仍然有方法、路径、状态码、Cookie 等概念，只是承载它们的传输和帧格式不同。

### 13.4 常见请求头分别表达什么

| 请求头 | 作用 | 隐私或行为提示 |
|---|---|---|
| `Host` | HTTP/1.1 中指定目标主机和可选端口 | 服务器据此选择虚拟主机；HTTP/2/3 也有等价的 `:authority` |
| `User-Agent` | 声明浏览器/操作系统标识 | 可用于兼容性和统计，也会增加指纹信息 |
| `Accept` | 声明可接受的媒体类型 | 影响服务器内容协商 |
| `Accept-Encoding` | 声明可解码的压缩算法 | 服务器可能返回 gzip、Brotli 或 zstd |
| `Accept-Language` | 声明语言偏好 | 可能影响语言和地区内容 |
| `Cookie` | 发送此前服务器设置的状态 | 可关联会话、登录和追踪标识 |
| `Sec-Fetch-*` | 描述导航/资源请求上下文 | 帮助服务器做 CSRF 和资源策略判断 |
| `Cache-Control` | 表达缓存验证或新鲜度意图 | 不等于一定绕过所有浏览器缓存 |

在 HTTP/2/3 中，伪首部如 `:method`、`:scheme`、`:authority`、`:path` 承担部分 HTTP/1.1 起始行和 `Host` 的职责。

### 13.5 Cookie、缓存和 Service Worker 的影响

“按下回车就发网络请求”不是必然。浏览器在导航前后可能检查：

- 强缓存是否仍新鲜；
- Service Worker 是否接管该 origin 的 fetch；
- Cookie 的 Domain、Path、Secure、SameSite、过期时间和隐私策略；
- 隐身模式、扩展、企业策略或内容拦截器；
- 是否需要先完成代理认证或门户认证。

即使最终没有访问源站，浏览器也可能在开发者工具里显示一个请求条目，因为请求可能被本地缓存或 Service Worker 生成了响应。

### 13.6 DNS、TCP、TLS 和 HTTP 的边界

这四者解决不同问题：

```text
DNS   ：www.baidu.com -> 一个或多个 IP
TCP   ：在两个 IP:port 之间提供可靠字节流
TLS   ：在连接上认证并加密字节
HTTP  ：定义“GET /”以及响应状态和资源语义
```

把 DNS 说成“建立连接”、把 TCP 说成“发送 HTTP 请求”、把 TLS 证书说成“服务器 IP 证明”，都是层次混淆。

## 14. 第十二步：百度一侧可能怎样处理请求

这里必须区分“从协议上必然发生的事”和“某个大型网站内部的具体实现”。我们可以可靠地描述典型互联网架构，但不能仅凭一个域名断言百度当前每个机房、服务名或内部组件的真实拓扑。

### 14.1 边缘节点和 CDN

DNS 可能把客户端引导到某个 CDN 或边缘接入地址。边缘节点首先接收 TCP/QUIC 和 TLS，随后处理 HTTP 请求。边缘选择可能综合客户端网络位置、运营商、健康状态、容量、策略和 BGP 路径。

边缘节点可能直接命中缓存，也可能把请求转发到更靠后的服务。即使响应来自 CDN，URL 仍然可以显示为 `www.baidu.com`；CDN 是部署和转发位置，不是另一个浏览器地址。

### 14.2 TLS 终止和证书选择

TLS 可以在边缘节点终止。该节点依据 SNI 选择证书，依据 ALPN 选择 HTTP/2 或 HTTP/1.1，然后解密出 HTTP 请求。边缘到后端之间可能继续使用 TLS，也可能在受控内网中使用其他安全机制；这属于站点内部设计，浏览器无法直接看到。

### 14.3 WAF、反爬和访问控制

请求可能经过 WAF（Web Application Firewall）或风控系统，检查：

- 请求方法、路径、头部格式和异常编码；
- 速率、连接数量、IP/ASN/地区声誉；
- Cookie、挑战令牌、浏览器行为信号；
- 注入、路径穿越、恶意 payload 等特征。

被拦截的请求可能收到 `403`、验证码页面、`429`，也可能被延迟或直接丢弃。返回这些结果不代表 DNS 或 TCP 一定有问题，因为它们说明请求已经到达了某个 HTTP 处理节点。

### 14.4 反向代理和负载均衡

反向代理位于客户端和应用服务器之间，通常负责：

- TLS 终止或透传；
- 根据 Host、路径、Cookie、版本进行路由；
- 连接复用、压缩、缓存和超时；
- 把请求分发到健康的后端实例。

负载均衡可以在 DNS、四层（按 IP/端口转发）或七层（理解 HTTP）完成。客户端只看到入口地址，不会看到每个后端实例的私网 IP。

### 14.5 缓存命中和缓存未命中

如果首页或静态资源在边缘缓存中仍新鲜，节点可能直接返回缓存对象；如果缓存过期，节点可能带着 `If-None-Match` 或 `If-Modified-Since` 向后端验证。后端若确认未变化，返回 `304 Not Modified`，正文可以为空。

动态页面、登录状态、个性化 Cookie、地理策略和不可缓存响应可能导致请求穿透到源站。缓存命中并不表示“服务器没有处理请求”，边缘仍需检查缓存键、权限、过期和安全策略。

### 14.6 应用服务器和内部服务

源站应用可能进行：

1. 解析 HTTP 请求和 Cookie；
2. 做登录、风控、实验分流和权限判断；
3. 查询缓存、搜索索引、数据库或其他内部服务；
4. 生成 HTML、JSON、重定向或错误页面；
5. 设置缓存策略、Cookie、安全头和压缩方式。

应用进程可能运行在容器、虚拟机或物理服务器上，使用线程池、事件循环、异步 I/O 和内部 RPC。浏览器并不知道这些内部调用，也不应该把“百度服务器”理解为一台固定机器。

### 14.7 服务器如何决定响应

典型逻辑可能是：

```text
请求到达边缘
  -> TLS 解密
  -> WAF/风控
  -> 缓存查找
       -> 命中：生成响应
       -> 未命中：反向代理转发
                      -> 应用逻辑
                      -> 内部缓存/数据库/服务
                      -> 生成响应
  -> 压缩、加安全头
  -> TLS 加密并发送
```

这是一种架构模型，不是对百度内部实现的事实披露。面试中应明确这一点，避免为了“讲得像内部专家”而编造组件名称。

## 15. 第十三步：HTTP 响应如何返回

### 15.1 状态码的含义

服务器先发送状态行（HTTP/1.1）或 `:status` 头（HTTP/2/3），再发送响应头和正文。常见结果包括：

| 状态码 | 典型含义 | 对浏览器的影响 |
|---:|---|---|
| `200` | 成功返回资源 | 进入正文处理和渲染 |
| `301`/`308` | 永久重定向 | 浏览器更新导航目标，可能再次 DNS/连接 |
| `302`/`303`/`307` | 临时重定向 | 按规则发起下一次导航 |
| `304` | 条件请求的缓存仍有效 | 使用本地缓存正文 |
| `403` | 服务器拒绝访问 | 显示拒绝页或挑战页 |
| `404` | 资源不存在 | 显示错误页面 |
| `429` | 请求过多 | 可能等待 `Retry-After` |
| `500`/`502`/`503`/`504` | 服务端或上游异常 | 显示服务器错误或重试 |

收到 `301` 并不等于 TCP 失败；它说明至少有一个 HTTP 节点成功处理并返回了应用层结果。

### 15.2 常见响应头

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Encoding: br
Cache-Control: no-cache
ETag: "example-version"
Last-Modified: Tue, 25 Aug 2026 00:00:00 GMT
Strict-Transport-Security: max-age=...
Set-Cookie: session_id=example-session; Secure; HttpOnly; SameSite=Lax
Content-Length: 12345

[compressed HTML bytes]
```

重要字段的层次如下：

- `Content-Type` 告诉浏览器如何解释正文；
- `Content-Encoding` 描述正文传输压缩，解压后才是 HTML 字节；
- `Content-Length` 是当前消息体长度，不一定存在（可能使用分块或 HTTP/2/3 DATA 帧）；
- `Cache-Control` 和 `ETag` 参与后续缓存验证；
- `Location` 指示重定向目标；
- `Set-Cookie` 请求浏览器保存状态；
- `Strict-Transport-Security` 告诉浏览器未来一段时间优先使用 HTTPS。

响应也可能使用 `Transfer-Encoding: chunked`（HTTP/1.1），或者在 HTTP/2/3 中通过 DATA 帧持续发送，不应把“没有 Content-Length”简单解释成传输失败。

### 15.3 返回路径

响应通常沿着连接的反向路径返回，但互联网路由不要求严格对称。服务器发出的 IP 包经过出口路由、运营商、互联点、接入网、家庭路由器，最后到达笔记本。家庭 NAT 根据连接状态把公网目的端口改回笔记本的私网地址和临时端口。

例如公网侧看到：

```text
203.0.113.20:443 -> 198.51.100.7:62001
```

家庭路由器把它映射回：

```text
203.0.113.20:443 -> 192.168.1.23:53142
```

之后路由器在局域网中用 ARP 或 NDP 找到笔记本网卡的 MAC。笔记本网卡把帧交给驱动，内核按 TCP 序列号重组，再把 TLS 记录交给浏览器网络进程。

## 16. 第十四步：浏览器如何把响应变成页面

“收到服务器响应”不等于“屏幕立刻显示页面”。网络、解析、样式、布局、绘制和显示是连续但相对独立的阶段。

### 16.1 从网卡到浏览器进程

典型接收链路是：

```text
网卡收到无线帧/以太网帧
  -> 驱动和 DMA 写入内核缓冲区
  -> 链路层校验、去掉帧头
  -> IP 层确认目的地址
  -> TCP/QUIC 重组和流量控制
  -> TLS 验证并解密
  -> HTTP/2 或 HTTP/1.1 解析
  -> 浏览器网络服务把数据交给渲染进程
```

浏览器通常采用多进程架构：浏览器主进程管理窗口和权限，网络服务处理连接，渲染进程解析页面，GPU 进程协助合成。不同浏览器和版本的进程边界会变化，但“网络数据不直接等于 DOM”这一点不变。

### 16.2 解压、字符集和 HTML 解析

浏览器先根据 `Content-Encoding` 解压，再根据 HTTP 头、HTML 元标签和规范推断字符编码。HTML tokenizer 把字节流转换为 token，树构建器逐步构造 DOM。HTML 解析具有容错性，遇到不完全规范的标记时不会简单地报错退出，而会按 HTML 解析规则修复树结构。

### 16.3 Service Worker 和缓存检查

若该 origin 注册了 Service Worker，导航或资源请求可能先经过其 `fetch` 事件。Service Worker 可以返回 Cache Storage 中的内容、转发到网络，或组合两者。浏览器还会查询内存缓存、磁盘 HTTP 缓存、预加载缓存和 BFCache 等机制。

因此服务器没有收到请求时，用户仍可能看到页面；反过来，开发者工具勾选“停用缓存”后，行为又会改变。

### 16.4 CSSOM 和渲染树

HTML 产生 DOM，CSS 文件和 `<style>` 产生 CSSOM。浏览器计算选择器匹配、继承、层叠和最终样式，形成包含可见节点的渲染树。`display: none` 的节点在 DOM 中存在，但通常不进入渲染树；伪元素可能没有独立 DOM 节点，却参与绘制。

### 16.5 样式计算、布局、绘制和合成

典型阶段可写成：

```text
DOM + CSSOM
  -> 样式计算
  -> 布局（每个盒子的几何位置和尺寸）
  -> Paint（生成绘制指令和图层内容）
  -> Raster（栅格化为像素）
  -> Compositing（合成多个图层）
  -> GPU/显示控制器
  -> 屏幕刷新
```

JavaScript 修改 DOM 或样式，可能触发重新布局（reflow）或仅重新绘制（repaint）。有些变换和滚动可在合成线程中完成，避免主线程重新布局。最终像素可能在 GPU 中栅格化和合成，再由显示器按刷新周期扫描输出。

### 16.6 脚本、事件循环和安全边界

JavaScript 在渲染进程的事件循环中执行。网络响应、定时器、用户输入、Promise 回调等进入任务或微任务队列。脚本可能创建新的资源请求、修改 DOM、触发布局，或者通过 Service Worker 改变请求路径。

同源策略以 origin（scheme、host、port）为边界限制脚本读取其他站点的数据；CORS、CSP、Cookie 的 SameSite 属性和混合内容策略进一步约束跨源行为。TLS 加密并不绕过浏览器的同源策略。

### 16.7 子资源请求为什么让流程变长

首页 HTML 往往只是第一批响应。解析过程中浏览器可能发现：

- 外部 CSS；
- JavaScript 模块或脚本；
- 图片、视频和字体；
- favicon、manifest、预加载资源；
- iframe 和广告/统计请求。

这些资源可能来自多个域名，需要各自进行缓存检查、DNS、连接复用或新连接、TLS 和 HTTP 请求。浏览器会并行调度，但受同源、优先级、连接数量、带宽、CPU 和渲染依赖约束。用户看到“页面打开”时，后台资源可能仍在加载。

### 16.8 首字节、首屏和完全加载不是同一时刻

常见时间点包括：

- DNS 完成；
- TCP 或 QUIC 连接完成；
- TLS 完成；
- TTFB（收到首字节）；
- 首次内容绘制（FCP）；
- 最大内容绘制（LCP）；
- `DOMContentLoaded`；
- `load` 事件；
- 网络空闲或应用自定义“完成”。

服务器已经返回 `200`，不代表浏览器已经完成布局和绘制；反之，页面显示出来也不代表所有异步请求结束。

  ^                         |

### 17.1 DNS 路径和 HTTPS 路径不是同一条“请求”

DNS 查询可能发给配置的递归解析器，而 HTTPS 连接发给 DNS 返回的业务地址。两者可能走不同的 IPv4/IPv6、不同的运营商出口、不同的 VPN 或代理策略。DNS 成功只说明名字解析阶段完成，不说明 `443` 可达；反过来，已有连接或缓存也可能让页面在本次没有 DNS 查询时打开。

### 17.2 典型延迟由哪些部分组成

总耗时可以粗略拆为：

```text
输入和浏览器调度
+ DNS 缓存未命中延迟
+ TCP 三次握手或 QUIC 建连
+ TLS 握手
+ 请求排队和服务器处理
+ 首字节返回
+ 下载、解压、解析、布局和绘制
```

连接复用、DNS 缓存、TLS 会话恢复、HTTP/2/3 多路复用可以减少前几项；无线重传、拥塞、跨地区路由、服务器排队、CPU 忙和脚本执行会增加后几项。

## 18. 一个完全虚构的报文示例

以下地址专门使用文档示例网段，不是当前百度真实地址：

```text
笔记本 Wi-Fi：192.168.1.23/24
家庭网关：192.168.1.1
递归 DNS：192.168.1.1 或运营商 DNS
示例业务地址：203.0.113.20
笔记本临时端口：53142
```

### 18.1 DNS 请求的逻辑封装

```text
Wi-Fi/以太网帧
  IPv4: 192.168.1.23 -> 192.168.1.1
    UDP: 53100 -> 53
      DNS question: A/AAAA www.baidu.com
```

若递归 DNS 需要向外查询，它会用自己的源地址和端口向根、TLD 或权威服务器发送新的 DNS 报文；这些查询不是笔记本直接逐个访问根服务器。

### 18.2 TCP SYN 的逻辑封装

```text
Wi-Fi 数据帧
  目的 MAC: 家庭网关的无线 MAC
  源 MAC：笔记本网卡 MAC
  IPv4: 192.168.1.23 -> 203.0.113.20
    TCP: 53142 -> 443, SYN, Seq=1000, MSS=1460
```

当帧离开家庭网络后，链路层源/目的 MAC 会在每一跳重新封装；端到端 IP 地址通常保持（NAT 设备可能改写地址），TCP 端口通常保持（PAT 设备可能改写公网侧端口）。

### 18.3 HTTP/1.1 请求的逻辑封装

```text
以太网/Wi-Fi 帧
  IP
    TCP 字节流
      TLS Record
        HTTP GET / + headers
```

在线路上通常只能看到外层地址、端口、长度、时序等元数据，而看不到被 TLS 加密的 `GET /` 和 Cookie。浏览器开发者工具能显示明文，是因为它位于本机 TLS 终止点之后，不是因为网络中传输了明文 HTTP。

### 18.4 为什么同一页面会有很多五元组

如果首页引用 `static.example`、图片 CDN 和字体 CDN，浏览器可能分别建立：

```text
(本机IP, 53142, 首页IP, 443, TCP)
(本机IP, 53143, 静态IP, 443, TCP)
(本机IP, 53144, 字体IP, 443, UDP/QUIC)
```

HTTP/2/3 可以让同一目的端点承载多个请求，但不同 origin、代理隔离键或协议选择仍可能需要不同连接。

## 19. 失败场景：看到什么现象，可能卡在哪里

| 现象 | 可能阶段 | 解释和优先检查 |
|---|---|---|
| Wi-Fi 图标未连接 | 无线链路 | 检查无线开关、AP 关联、信号、驱动 |
| 有 Wi-Fi 但没有 IPv4 地址 | DHCP | `ipconfig /all` 看 DHCP、地址、租约和网关 |
| 有地址但访问所有外网超时 | 默认路由/网关 | `route print`、网关连通性、路由器 WAN 状态 |
| 只有域名打不开，直接 IP 可能可达 | DNS/HOSTS | 检查 HOSTS、DNS 缓存、递归 DNS、DoH/DoT |
| `NXDOMAIN` | 名字不存在 | DNS 明确回答该名字不存在，通常不是 TCP 问题 |
| `SERVFAIL` 或 DNS 超时 | 解析器/链路/验证 | 递归服务器故障、DNSSEC、网络丢包或策略拦截 |
| 解析到奇怪的本地 IP | HOSTS/恶意软件/DNS 污染 | 对比可信解析器，检查 HOSTS 和代理扩展 |
| ARP 解析不到网关 | 局域网二层 | 检查 VLAN、无线隔离、网关、网卡和邻居表 |
| IPv6 连接慢，随后 IPv4 成功 | IPv6 路径异常 | Happy Eyeballs 让浏览器回退；检查 RA、NDP、IPv6 防火墙 |
| DNS 成功但 `443` 连接超时 | 防火墙/路由/端口可达性 | `Test-NetConnection`，再看代理/VPN和中间设备 |
| 立即 `connection refused` | 对端或中间设备主动拒绝 | 端口无监听、策略拒绝或 RST |
| TLS 证书域名不匹配 | TLS 身份验证 | URL、SNI、代理重签发、系统时间、信任库 |
| 仅浏览器打不开，命令行能开 | 浏览器状态 | 缓存、扩展、Service Worker、代理设置、QUIC 状态 |
| 仅公司网络打不开 | 企业策略/代理 | PAC、认证代理、企业 CA、出口防火墙 |
| 跳到登录/验证码页 | 门户/WAF/风控 | HTTP 已到达某个应用层节点，不是纯 DNS 故障 |
| `301`/`302` 很多次 | 重定向配置 | 查看 `Location` 链，可能跨域并重新解析连接 |
| `403` | 权限/WAF/区域策略 | 请求到达服务器但被拒绝 |
| `429` | 速率限制 | 降低并发，观察 `Retry-After`，不要盲目重试 |
| `502`/`504` | 代理到上游失败 | 边缘可达，但后端连接或响应超时 |
| 页面部分加载后卡住 | 子资源/脚本/MTU | 看 Network waterfall、控制台、丢包和路径 MTU |
| 小请求正常，大响应失败 | MTU/PMTUD/代理 | 检查 ICMP、MSS、VPN/PPPoE 封装和中间防火墙 |
| 页面显示旧内容 | 浏览器/Service Worker/CDN 缓存 | 查看 `Age`、`ETag`、Cache Storage 和强缓存策略 |

### 19.1 “对方主机断开连接”与不同错误的区别

面试中常把所有失败都称为“对方断了”。实际至少要区分：

- DNS 没有结果：连接根本尚未开始；
- SYN 超时：包可能没到对端或响应被过滤；
- RST：某个 TCP 端点或中间设备明确终止；
- TLS alert：TCP 已建立，但安全协商失败；
- HTTP `4xx/5xx`：应用层已经返回了结果；
- 浏览器渲染错误：网络可能成功，页面脚本或资源处理失败。

不同层的错误需要不同证据，不能只看浏览器的一句“无法访问此网站”。

## 20. Windows 上如何观察这条链路

以下命令以 PowerShell 或命令提示符为例。命令能证明的范围有限，不能把一次成功测试外推成所有浏览器行为。

### 20.1 本机地址、网卡、网关和 DNS

```powershell
ipconfig /all
```

可观察网卡名称、MAC、IPv4/IPv6、DHCP、默认网关、DNS 服务器和租约。它不能证明浏览器使用了哪个地址，也不能显示全部代理或 Service Worker 逻辑。

```powershell
Get-NetIPConfiguration
Get-NetAdapter
Get-DnsClientServerAddress
```

这些 PowerShell 命令以更结构化的方式查看接口、状态和解析器配置。

### 20.2 HOSTS 和 DNS 缓存

Windows HOSTS 通常位于：

```text
C:\Windows\System32\drivers\etc\hosts
```

查看内容需要管理员权限时，只读打开即可；不要为了测试随意修改系统文件。

```powershell
ipconfig /displaydns
ipconfig /flushdns
nslookup www.baidu.com
Resolve-DnsName www.baidu.com -Type A
Resolve-DnsName www.baidu.com -Type AAAA
```

`displaydns` 只显示 Windows DNS Client 缓存，未必包含浏览器自己的缓存；`flushdns` 只清系统缓存，不能清浏览器缓存、路由器缓存或递归 DNS 缓存。`nslookup` 默认向指定解析器查询，不能自动复现浏览器 DoH、代理或所有地址选择逻辑。

### 20.3 邻居表和路由表

```powershell
arp -a
Get-NetNeighbor
route print
Get-NetRoute -AddressFamily IPv4
Get-NetRoute -AddressFamily IPv6
```

这些命令可帮助确认网关 MAC、邻居状态和最长前缀匹配结果。邻居表为空不一定是故障，条目可能已过期或尚未触发通信。

### 20.4 端口连通性和 TLS/HTTP 观察

```powershell
Test-NetConnection www.baidu.com -Port 443 -InformationLevel Detailed
curl.exe -I -v https://www.baidu.com/
```

`Test-NetConnection` 主要测试 DNS、路由和 TCP 端口，通常不完成浏览器级别的 HTML 渲染；`curl -v` 可以显示解析、连接、TLS 和 HTTP 头部线索，但它的代理、证书库、HTTP/2/3 和 Cookie 行为可能与浏览器不同。

查看浏览器开发者工具的 Network 面板时，重点记录：

- `Status`、`Remote Address`、协议版本（h2/h3/http/1.1）；
- `Timing` 中 Queueing、DNS、Initial connection、SSL、TTFB、Content Download；
- Request URL、重定向链、缓存状态和响应头；
- 是否显示 `(from disk cache)`、`from ServiceWorker` 或 `304`。

### 20.5 tracert 和抓包

```powershell
tracert www.baidu.com
pathping www.baidu.com
```

它们使用 ICMP 或探测报文推断路径，沿途设备可能限速或丢弃探测，因此不一定代表 HTTPS 数据的实际完整路径。

Wireshark 可使用类似过滤器：

```text
dns
arp or icmp or icmpv6
tcp.port == 443
udp.port == 443
tls
quic
```

抓包位置非常重要：在浏览器主机上可以看到本机到网关的帧和加密流量，但看不到服务器内部明文；在 TLS 终止点或配置了会话密钥的调试环境，才可能进一步分析 HTTP 内容。抓取他人流量必须遵守授权、隐私和法律要求。

### 20.6 端口和进程归属

```powershell
Get-NetTCPConnection -State Established |
  Sort-Object RemotePort |
  Select-Object LocalAddress,LocalPort,RemoteAddress,RemotePort,OwningProcess

Get-Process -Id 1234
```

这有助于把一个连接四元组关联到浏览器或其网络服务进程。但现代浏览器多进程、连接池和代理会让“某个标签页 = 某个 TCP 连接”的映射不成立。

## 21. 面试回答模板

### 21.1 30 秒版本

用户按下回车后，浏览器解析 URL，先检查自身和系统缓存以及 HOSTS；若没有地址，就通过系统解析器向递归 DNS 查询 `www.baidu.com` 的 A/AAAA 记录。操作系统依据路由表选择网卡和下一跳，必要时用 ARP/NDP 找到网关 MAC；数据经过 Wi-Fi、家庭路由器的 NAT/防火墙、运营商和互联网路由到达百度边缘节点。浏览器随后通过 TCP+TLS 或 QUIC 建立安全连接，协商 HTTP/1.1、HTTP/2 或 HTTP/3，发送 GET 请求。服务器经 CDN、WAF、反向代理、缓存和应用服务生成响应；响应沿网络返回，浏览器解密、解压、解析 HTML/CSS/JavaScript，构建 DOM/CSSOM，布局、绘制并由 GPU 合成到屏幕，同时继续加载子资源。

### 21.2 2 分钟版本的展开顺序

按“输入 -> 解析 -> 寻址 -> 建连 -> 加密 -> 请求 -> 服务端 -> 返回 -> 渲染”九个动词讲，每个动词只补一到两个关键细节：

1. 输入：键盘事件经过驱动和窗口系统到地址栏。
2. 解析：URL 规范化，判断 scheme、host、port 和路径。
3. 寻址：浏览器缓存、HOSTS、DNS Client、递归 DNS，得到 A/AAAA。
4. 建连：路由表、ARP/NDP、网卡、TCP 三次握手或 QUIC。
5. 加密：TLS ClientHello、SNI、证书链、ALPN、会话密钥。
6. 请求：HTTP GET、`Host`、Cookie、缓存和压缩协商。
7. 服务端：边缘/CDN、WAF、反向代理、缓存、应用和内部服务。
8. 返回：状态码、响应头、压缩正文，经过 NAT 和 TCP/QUIC 重组。
9. 渲染：解密解压、DOM/CSSOM、布局、绘制、合成，以及子资源并行请求。

### 21.3 10 分钟版本的重点

长答时应主动指出以下边界和变体：

- `www.baidu.com` 不一定先访问 HTTP 80，可能直接 HTTPS 或被重定向；
- DNS 可能被浏览器缓存、HOSTS、系统缓存、DoH/DoT、代理或 VPN 改变；
- IP 地址在三层转发，MAC 地址只在当前链路有效；
- NAT 改写地址/端口，代理则是应用层的另一跳；
- IPv6、Happy Eyeballs、QUIC/HTTP/3 可能让路径不同；
- 服务器内部架构只能讲典型模式，不能凭域名猜具体组件；
- HTTP `200`、TLS 成功和页面完全绘制是三个不同时间点。

## 22. 常见面试陷阱

### 22.1 “浏览器先查 HOSTS，再查 DNS”说得太绝对

实际调用链由浏览器、操作系统名称解析 API、安全软件和网络策略共同决定。HOSTS 通常参与系统解析，但浏览器可能有自己的解析器或 DoH。更严谨的说法是：“先检查可用的本地解析来源，包括浏览器缓存、系统缓存和 HOSTS；未命中时再按当前解析策略查询 DNS。”

### 22.2 “拿到 IP 后先 ARP 服务器”

如果服务器不在本地二层网段，笔记本 ARP 的是默认网关，不是远端百度服务器。每一跳只解析自己的下一跳链路地址。

### 22.3 “TCP 连接就是 HTTP 连接”

TCP 只提供字节流。TLS 可以运行在 TCP 之上，HTTP 再运行在 TLS 之上；同一条 TCP/TLS 连接还可以承载多个 HTTP/2 请求。

### 22.4 “HTTPS 加密了所有信息”

HTTPS 保护应用内容和完整性，但 IP、端口、流量时序等元数据可能仍可见；传统 SNI 和未加密 DNS 也可能泄露主机名。

### 22.5 “一次网页访问只有一个请求”

首页 HTML 只是导航起点。CSS、脚本、图片、字体、iframe、广告和遥测会产生更多请求，而且可能访问不同域名。

### 22.6 “DNS 返回的 IP 就是源站服务器 IP”

大型站点常使用 CDN、Anycast、反向代理、负载均衡和多地域入口。DNS 返回的是当前解析策略下可访问的地址，不必然是存储业务数据的源站。

### 22.7 “tracert 显示的路径就是浏览器路径”

探测包的协议、目的地址、TTL、时间和策略都可能不同。中间路由器不回应探测，也不代表它不转发 HTTPS。

### 22.8 “看到 200 就说明页面没问题”

状态码只描述一个 HTTP 响应。正文可能是错误页，脚本可能报错，关键子资源可能失败，或者页面仍在异步加载。

## 23. 术语表

| 术语 | 一句话解释 |
|---|---|
| URL | 描述资源定位和访问方式的字符串，如 scheme、host、port、path |
| HOSTS | 本机静态的主机名到地址映射文件 |
| DNS | 把域名等名称解析为 IP 或其他记录的分布式系统 |
| resolver | 代表应用发起名称解析的客户端组件/接口 |
| 递归 DNS | 代替客户端查询并缓存结果的解析服务器 |
| 权威 DNS | 对某个域名区域拥有最终记录的服务器 |
| A | DNS 中的 IPv4 地址记录 |
| AAAA | DNS 中的 IPv6 地址记录 |
| CNAME | DNS 中的规范名称别名记录 |
| TTL | 在不同上下文中表示 IP 跳数限制或 DNS 缓存时间，需看所属层 |
| 网卡/NIC | 连接主机与网络介质的硬件或虚拟接口 |
| MAC | 链路层接口地址，通常只对本地链路有意义 |
| ARP | IPv4 中通过 IP 找局域网 MAC 的协议 |
| NDP | IPv6 中基于 ICMPv6 的邻居发现机制 |
| IP | 负责跨网络寻址和尽力转发的数据报协议族 |
| 路由表 | 决定目的地址下一跳和出接口的规则集合 |
| 端口 | 操作系统将网络流量交给具体 socket 的逻辑编号 |
| socket | 应用与内核网络栈交互的通信端点抽象 |
| TCP | 有序、可靠、面向连接的字节流传输协议 |
| UDP | 无连接数据报传输协议，不自带可靠性保证 |
| QUIC | 在 UDP 上实现可靠多路复用并集成 TLS 的传输协议 |
| TLS | 提供认证、机密性和完整性的安全协议 |
| SNI | TLS ClientHello 中指示目标主机名的扩展 |
| ALPN | TLS 中协商应用协议名称的扩展 |
| HTTP/1.1 | 以文本起始行和头部表达 HTTP 的传统版本 |
| HTTP/2 | 使用二进制帧、头部压缩和多路复用的 HTTP 版本 |
| HTTP/3 | 映射到 QUIC stream 的 HTTP 版本 |
| NAT | 在网络边界改写地址的机制 |
| PAT | 通过端口区分多个内部连接的 NAT 形式 |
| CGNAT | 运营商级的大规模 NAT |
| 代理 | 代表客户端在应用层发起下一跳请求的中间服务 |
| VPN | 通过虚拟接口和隧道封装改变流量路径的技术 |
| CDN | 分布式内容交付和边缘缓存网络 |
| WAF | 识别和拦截 Web 层攻击或异常请求的防护组件 |
| 反向代理 | 代表服务器接收客户端请求并转发后端的服务 |
| 负载均衡 | 把连接或请求分配到多个后端实例的机制 |
| DOM | 浏览器根据 HTML 构建的文档对象树 |
| CSSOM | 浏览器根据 CSS 构建的样式对象模型 |
| 渲染树 | 结合 DOM 和样式后用于布局绘制的可见节点结构 |
| reflow/layout | 计算元素几何位置和尺寸的阶段 |
| paint | 生成绘制背景、文字、边框等内容的阶段 |
| compositing | 将多个图层合成为最终画面的阶段 |
| GPU | 可并行处理图形栅格化和图层合成的处理器 |
| MTU | 某一链路可承载的最大 IP 包大小 |
| MSS | TCP 单个段建议承载的最大应用负载 |
| BGP | 自治系统之间交换可达前缀和路径属性的协议 |
| AS | 由一个组织或管理策略控制的自治系统 |

## 24. 最后把整件事压缩成一句准确的话

在笔记本上输入 `www.baidu.com` 后，键盘事件先被操作系统交给浏览器；浏览器解析 URL 并按本地缓存、HOSTS、系统解析器和 DNS 策略把域名解析成候选 IP。内核依据路由表选择网卡和下一跳，借助 ARP/NDP 找到局域网链路地址，数据经过 Wi-Fi/以太网、家庭路由器的 NAT 与防火墙、运营商和互联网逐跳路由到百度的边缘入口。浏览器随后用 TCP+TLS 或 QUIC 建立并认证加密通道，协商 HTTP/1.1、HTTP/2 或 HTTP/3，发送带有 `Host` 等头部的 HTTP 导航请求。服务端经过边缘、WAF、反向代理、缓存和应用服务生成响应，响应沿连接返回；浏览器解密、解压、解析 HTML/CSS/JavaScript，构造 DOM/CSSOM，完成样式计算、布局、绘制和 GPU 合成，最后在屏幕上显示像素，并继续为页面的子资源发起后续请求。

## 25. 阅读和验证本文件时的说明

1. 文档采用 Windows 10/11、Chrome/Edge 类浏览器、Wi-Fi、家庭路由器、双栈网络作为主示例；macOS/Linux、有线网络、企业代理、VPN、IPv4-only、HTTP/3 会改变局部步骤。
2. `203.0.113.20`、`198.51.100.7` 等是文档示例网段，不能当作百度当前真实地址。
3. 百度实际的 CDN、机房、WAF、负载均衡和源站拓扑属于动态且未在本文件中实时核验的内部实现；文中只描述通用架构模型。
4. 一个命令只能证明它所在层的部分事实。例如 `nslookup` 不能证明浏览器已完成 TLS，`Test-NetConnection` 不能证明 HTML 可渲染，`tracert` 不能证明 HTTPS 的精确数据路径。
5. Markdown 文件应使用 UTF-8 读取。PowerShell 旧版本不指定 `-Encoding utf8` 时可能把中文显示成乱码，但这不等于文件损坏。
